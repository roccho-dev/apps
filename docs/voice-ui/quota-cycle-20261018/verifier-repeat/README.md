# 正しい部品集合の受理を先に確かめる

問いは「原文から一意に決まる新規部品の表示名・種類・総個数と、この候補は過不足なく一致するか」です。
候補と原文は既存のstateで渡し、completenessの問いだけを短くします。因子・受理閾値0.5・生成方式・描画は変えません。

## 直前までに分かったこと

[前回の公開E試験](../typed-repeat/README.md)では、新しいTypeLLM候補がAPI/step/2を正確に出しました。
ただし既存Vのcompletenessはcomplete/0.46で、閾値未満の保留となり、描画へ進みませんでした。
B/Cとも0/1、改善0です。候補生成の成功と、製品の完成は分けます。
前回の封印E6はRoot未開封・未実行のままです。
[独立レビューR26](https://github.com/roccho-dev/apps/pull/103#pullrequestreview-5561538864)は、保存結果とCIの閉包についてGREENです。

## 今回の小さな工程

同じ候補を、公開V6 → 公開E1ペア → 封印E6ペアの順に評価します。
V6は正しい候補1つを受理し、誤った候補5つを拒否することを要求します。
正解率だけでなく、raw因子と低確信の保留も残します。V6には比較対象がないため、旧Vより改善したとは主張しません。
Vが未達・無効ならEへ進みません。公開Eが未達・無効なら封印E6を開きません。
封印E6は前回未実行の同一原本を今回も再登録し、選び直しません。

| 評価する能力 | 合格の範囲 | 現在 |
| --- | --- | --- |
| 揃った部品を表現する | 既存の独立供給R試験・描画証拠 | 有限範囲で合格、今回の変更対象外 |
| 部品集合の正誤を判定する | 公開V6で受理1・拒否5、誤受理0 | 今回は未測定 |
| 不足を補い描画する | 公開E通過後、封印Eで既存の完成・改善・安全条件 | 今回は未測定 |

## 打開策の優先順位（主観）

| 順位 | 打開策 | 優先する背景 |

| 1 | 候補照合の問いを小さくし、正しい集合の受理と誤った集合の拒否を同時測定 | 直前は正しい生成候補が判定で止まった |

| 5 | thinking増量・表現拡張 | 現時点の判定不全の解決に直接結びつく証拠がない |
