問いは「明示された表示名・種類・総NEW個数を、どの条件なら忠実に返せるか」。[adrs#449](https://github.com/roccho-dev/adrs/issues/449)に従い、目的・事実・評価・境界を共有し、不要な方法指定や監査基盤を増やさない。

部品供給済みの表現R2/2、不足補完0/2という[前回結果](../quota-cycle-20261018/README.md)は保持する。表示名保持指示、在庫差分、低confidence保留は既存であり、新しい打開策と数えない。原文名が汎用名へ置換された箇所は分かるが、質問・型・文脈・モデルの内部原因は未証明である。

## 今回の小さい境界

製品実装は変更せず、全4CIと[R22](https://github.com/roccho-dev/apps/pull/103#pullrequestreview-5560754656)を通したApps `fe6329ea55bde8f44293be9c17c39a97a2a1dc1d`の完成物を測る。公開登録を保存したcommitと、測定する完成物のcommitを混同しない。

既存の `/api/parts/requirements` だけを用いる。Jev判定、図の組み立て、描画、保存はこの診断では実行しない。公開済みQE03/04は表示名・種類・個数が原文に明示されている。将来の未見入力と旧未使用sealは読まない。

Defs空は、この抽出専用APIへの入力partsを空にして実現する。原文・既存regions・head・edges・その他schema/質問/型・provider・モデル・温度を保持する。差が出ても、kind→label一本、標準名だけ、あるいはモデル一般を原因と断定しない。定義が必要な一般依頼へ外挿しない。

[固定計画](diagnostic.json)の2入力×4条件×2回、計16枠を事前固定順で逐次実行する。2回目も予定済みの測定で、失敗の再試行ではない。応答による順序変更・修正・欠測置換はしない。

## 評価と証拠

[公開正解と評価条件](diagnostic.oracle.json)はcallerへ入力しない。全16枠を分母に保持し、原request/response、観測済HTTPエラー・契約拒否、構造INVALID、応答なしの通信不明、意味誤り、完全一致を分ける。有効応答には閉response・request_id・slotsとrequiredの一致も要求する。同じcase/repで双方が有効な組だけ意味精度を比較し、契約成立率の差は別記する。

同じ完成Workerをキー不要で動かして捕捉するType送信bodyと、公開HTTP原bytes・完成物/source同一性で因子差を束縛する。これはfixture応答による送信形式検証であり、live upstream bodyを直接保存した証拠でも、モデル品質でもない。typellm-latestの解決先モデル版は未観測とする。実測原応答とprovider送信ログは別に保持する。鍵本体・headers・環境全体は記録しない。

結果が繰り返し一貫すれば、その有限条件を次の仮説候補とする。混在なら判別未成立、全条件同じなら今回の比較では切り分けられなかったとする。製品EFFECTやNO_EFFECT、未見品質、Type一般の有効・無効へ昇格しない。

## 予算・工程・停止

rootがcallerと実行、同じ独立担当1名が契約・完成物・送信0・原応答・精算を独立確認する。公開登録とwire差の確認 → 同じ実プロセスの送信0を双方が確認 → 16枠実行 → 物理停止・精算 → 独立評価、で一度閉じる。開始前の不一致やcap超過懸念は実送せず停止する。実行中の各HTTP失敗はその枠を保持し、残る予定枠だけを実行する。最終停止不成立・送信数不明は次段へ進まない。

候補変更、新規4例の未見抽出比較、通常UIでの補完・描画比較は、今回の結果を受けて別に条件と上限を固定する。今回のphaseをその実送許可へ自動転用しない。AppsのdraftとUI#362の人間merge条件を保持する。

## 停止済みの結果

[原16件](evidence/public-A/raw/)と[集計](result.json)を保存した。[同じ独立担当の検算](evidence/public-A/independent-stopped.json)も一致した。

| 条件 | 全枠 | 契約成立 | 正答 | 有効だが意味誤り | HTTP契約拒否 |
| --- | ---: | ---: | ---: | ---: | ---: |
| DF・依存あり／定義あり | 4 | 4 | 1 | 3 | 0 |
| IF・依存なし／定義あり | 4 | 2 | 0 | 2 | 2 |
| DE・依存あり／定義なし | 4 | 4 | 2 | 2 | 0 |
| IE・依存なし／定義なし | 4 | 2 | 2 | 0 | 2 |

通信不明0。QE03の「出荷可否」は定義なしで各2回とも正答した。現行DFは正答と誤名が1回ずつであり、揺れも観測した。QE04の「APIを2個」は全条件で未解決。依存なしのQE04は4件とも契約拒否だったが、拒否された生成値そのものは取得しておらず、その誤りの種類は断定しない。

有効両対に限るDF→DEは4組中gain1／regression0。IF→IEは有効2組中gain2／regression0、残る2組は契約不成立で意味比較に含めない。契約成立率の差を意味精度の改善へ足さない。

判定は**QE03についての条件仮説あり、両例を安定して解決する打開策は未達**。空定義の一般採用、内部原因、解決先モデル版、未見品質、通常UIでの補完・表現効果は未証明。供給済みの表現性能と、不足部品を揃える性能は引き続き別に扱う。

16枠開始前の2起動でNix公開fetchの証明書エラーが見えたため、測定へ進めず停止した。最終原ログでは両方とも停止前にlistenへ到達しており、「起動不能」とは判定しない。両方0J/0Tで停止・精算し、[原記録](evidence/public-A/bootstrap/)を保持した。既存managerのbootstrapへ固定NSS CA指定2変数だけを引き継ぎ、同じlauncher・FD経路・完成物・計画でA3を実行した。証明書検証、鍵、製品は変更していない。

[停止・精算](evidence/public-A/orchestration.json)は追加0J/16T、累計charged847J/104T（確認847/103、過去不確定Type1を保持）、予約0。[最終観測](evidence/public-A/root-terminal.json)と独立観測で全45所有process groupがZを含め不在。CIは原応答・固定順・段階ログ・有限比較・台帳を再計算する。CIからの実API起動や通常UI描画を行った証拠にはしない。
