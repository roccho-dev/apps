## Proposed wire and stage contract for R sealing
Quantity always means the total number of requested NEW additions before subtracting either stock or existing Working nodes.

- Default normal API policy is adaptive-v2. Explicit check modes literal-v2 (disabled baseline) and adaptive-v2 (enabled) share the identical initial canonical B proposal and G0 question. Legacy literal/typed routes remain identifiable as v1.
- POST /api/parts/requirements accepts the existing inventory request and runs the same full-required generator used inside adaptive-v2, with one Type call. It returns a versioned closed required proposal, approved required1/2/3 slot values and an app-owned request_id.
- POST /api/parts/verify accepts a closed inventory-state + required tuple request (no oracle or expected result), calls the same verification function/compiled Worker path used inside adaptive-v2 with one Jev call, and returns a versioned closed verification receipt with required, all four named factors, derived accepted/confidence and request_id.
- Each active required slot has exactly label/kind/quantity, label within the existing label bound, kind from the existing supported enum and quantity 1..3. Unused kind-none slots are padding, not requirements. Active pairs are distinct and total NEW quantity<=3. Do not reuse the missing-only typed request/schema for this route.

The check response remains choice/confidence/inspection. Inspection v2 contains exactly:
schema, request_id, mode, initial, proposal, verification, required, missing.
initial contains decision, factors, literal, observation:
- decision is the actual G0 choice/confidence, never rewritten from G-prime;
- factors are the closed intent/labels/capacity/completeness choice/confidence records;
- literal is an internally consistent recognized/required/spans proposal (empty if raw parser syntax is invalid);
- observation holds bounded parser validity/status diagnostics, distinct from the adoptable literal proposal.
proposal is null or the approved closed Type slots plus their decoded full required tuples.
verification is null or its actual closed four named factors. Labels/capacity factors are diagnostic; only accepted change + complete authorize preparation.
required is the latest full required multiset, and missing is the app's recomputable one-use stock difference. A rejected proposal may be recorded but cannot be materialized.

An app-owned request_id and explicit G0/TYPE_REQUIRED/VERIFY_REQUIRED/STOCK_DIFF stages bind the actual HTTP result to source stdout. Preserve only approved closed Type slot values; unknown fields, raw upstream bodies and upstream headers are not saved, only bounded structural diagnostics. Raw invalids remain INVALID/UNPROVEN and are never retried. No Type-generated IDs appear in proposals.

Use one40-second bounded check deadline/abort for both v2 arms and propagate its remaining shared signal through G0/Type/V, checking it before each send. The original whole-Goal deadline remains. Count1HTTP check separately from the actual initial Jev + conditional Type + verification Jev sends. Keep deterministic preparations/materialization separate from real HTTP complete callbacks; preparing from an already verified receipt must not call Type again.

Live E selects only the registered literal-v2/adaptive-v2 policy through actual supported HTTP routes on the same compiled Worker. The enabled arm is the normal default. Record both the ordinary browser request and actual upstream policy URL; do not inject cached or synthetic model answers. Pair order is fixed/alternated in advance and every arm starts from identical initial raw bytes. The mode enum and normal default are fixed in each producer.
